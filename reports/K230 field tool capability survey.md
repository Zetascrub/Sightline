# Build Sightline into a trustworthy field instrument

**Sightline should become a tool-rich, evidence-first handheld for authorized assessments**, centered on bounded network discovery, packet capture, protocol checks, asset history, and export to a companion workstation. The LILYGO T-Display K230 has a much larger touch display and a Linux software base than the ESP32 handhelds in this survey, and the attached keyboard makes target entry, filtering, and terminal-style inspection practical. Its current project record confirms display, touch, keyboard, ordinary Wi-Fi, USB Ethernet, local BLE scanning, and outdoor GNSS, but it does **not** establish monitor-mode Wi-Fi, frame injection, USB HID gadget operation, or a BlueZ-compatible BLE adapter. The best lessons from Bruce, Marauder, Biscuit, and Hak5 are operational: make each capability discoverable, show its hardware prerequisites, let an operator select an authorized scope and one operation, keep raw artifacts, and make stop and export obvious. Native Nmap and `tcpdump` integration already give Sightline a foundation; the next release should deepen that foundation before claiming every portable firmware feature. ([Sightline README](https://github.com/Zetascrub/Sightline/blob/main/README.md)) ([Sightline development log](https://github.com/Zetascrub/Sightline/blob/main/DEVELOPMENT.md)) ([Bruce capability matrix](https://github.com/BruceDevices/firmware))

## The display and keyboard can carry a serious workflow

The board's **4.1-inch, 568 × 1232 AMOLED** is large enough for an assessment dashboard, long evidence views, and a split target/results layout in landscape orientation. LILYGO specifies a dual-core 64-bit RISC-V K230 and hardware acceleration blocks, while its board repository identifies the RM69A10 panel, Goodix GT9895 touch controller, MIPI DSI path, and GC2093 camera. Sightline's tested Linux image uses DRM/KMS and LVGL rather than a conventional framebuffer; its development log records Buildroot 2025.02.1, Linux 6.6.36, and a working physical touch proof. The separate CanMV board specification lists 1 GiB LPDDR, but that is **not a measurement of free memory under Sightline's running Linux image**. Any large scanner or local analysis daemon still needs a live RAM, storage, thermal, and battery profile. ([LILYGO product page](https://lilygo.cc/products/t-display-k230)) ([LILYGO board repository](https://github.com/Xinyuan-LilyGO/T-Display-K230)) ([Sightline development log](https://github.com/Zetascrub/Sightline/blob/main/DEVELOPMENT.md)) ([CanMV board specification](https://github.com/Xinyuan-LilyGO/T-Display-K230_canmv_rt/blob/main/README.md))

The optional keyboard expansion is a **TCA8418 I²C matrix controller at address `0x34`**, not a plug-and-play USB keyboard. The vendor pin map places it on I2C4 at GPIO47/46, with reset, interrupt, and backlight on separate pins; that bus also serves the charger, fuel gauge, GPIO expander, and possible haptic controller. Sightline's own board diagnosis found working keys and fuel-gauge telemetry through software-driven, open-drain GPIO46/47 transactions, rather than the initially assumed `/dev/i2c-0`; its keyboard driver currently polls the controller's event FIFO. This makes a keyboard-led command palette, target editor, filter bar, and operation shortcuts attractive, but a second daemon must not independently drive the shared lines. The latest physical text-edit and touch-typing workflow still needs acceptance on the actual unit, and the exact key matrix, rollover, and scan latency have not been established. ([Vendor pin map](https://github.com/Xinyuan-LilyGO/T-Display-K230/blob/main/k230_bsp/docs/HARDWARE_PINMAP.md)) ([Sightline keyboard driver](https://github.com/Zetascrub/Sightline/blob/main/src/tca8418_keyboard.h)) ([Sightline validation report](https://github.com/Zetascrub/Sightline/blob/main/docs/VALIDATION.md))

**Ethernet and ordinary IP networking are the dependable first path.** Sightline reports successful `wlan0` scans and wired DHCP through USB Ethernet. Its BLE scan uses an nRF52840 UART bridge at `/dev/ttyS1`, while no BlueZ `hci0` was observed on the tested image, so packages expecting a Linux HCI adapter cannot be promised on that path. The vendor BSP describes USB host, SD storage, optional LoRa, and different Wi-Fi chipsets from those recorded on Sightline's unit; these revision differences matter more than a generic K230 feature list. Kendryte documents gadget-capable USB builds, but the tested unit did not enumerate as a USB device in the older project observation. USB HID, serial, or Ethernet gadget modes therefore need a port-role and kernel-config proof on the actual image before becoming product features. ([Sightline development log](https://github.com/Zetascrub/Sightline/blob/main/DEVELOPMENT.md)) ([Vendor BSP guide](https://github.com/Xinyuan-LilyGO/T-Display-K230/blob/main/k230_bsp/README.MD)) ([Kendryte USB application guide](https://github.com/kendryte/k230_docs/blob/main/en/02_applications/tutorials/K230_USB_Application_Practice_UVC_Transmission_YUV_and_Encoding_Stream.md))

## Portable firmware points to modular tools and durable captures

Cardputer ADV firmware provides the strongest menu-design reference, while CardputerZero is a distinct Linux-class device rather than a firmware-compatible successor. **Bruce** publishes a broad capability matrix spanning Wi-Fi discovery, wardriving, BLE, IR, RF, NFC, USB HID, file management, network clients, and a web UI, while marking several features as dependent on external modules. **ESP32 Marauder** exposes a clear scan, target, channel, capture, and stop vocabulary, and documents hardware-specific binaries; its behavior cannot be transplanted to the K230 radio by copying an interface. **NEMO** adds passive detector ideas, including suspicious Wi-Fi/BLE activity and USB device inspection. CardputerZero's quad-core Cortex-A53, 512 MB RAM, keyboard, USB roles, Ethernet, and microSD make it a closer form-factor comparison, although M5Stack still describes its software development as in progress. These projects support a **capability matrix per physical adapter and firmware image**, with the UI explaining which operations are actually available. ([Bruce source and matrix](https://github.com/BruceDevices/firmware)) ([Marauder CLI](https://github.com/justcallmekoko/ESP32Marauder/wiki/CLI)) ([Marauder hardware versions](https://github.com/justcallmekoko/ESP32Marauder/wiki/marauder-versions)) ([NEMO source](https://github.com/n0xa/m5stick-nemo)) ([CardputerZero documentation](https://docs.m5stack.com/en/CardputerZero))

Biscuit Pro, Ultra, and Crumb offer a particularly useful capture model. Their documentation describes AP and station inventory, channel/security/RSSI filtering, Wi-Fi and BLE surveys, PMKID/EAPOL observation, PCAP export, and a history that survives controller disconnection; Ultra's microSD capture can continue after its phone loses contact. Biscuit's distributed Node documentation also makes an important radio constraint explicit: one single-radio node is assigned Wi-Fi **or** BLE work during a wardrive. Sightline should record interface identity, channel dwell, dropped or skipped packets, GPS source, and capture gaps as first-class evidence, and resume display/control after a connection interruption without pretending that lost packets were collected. Biscuit's public repositories inspected here are flashers; this survey found no official source tree or license for the Pro/Ultra/Crumb device firmware, so these are workflow references, not code to import. ([Biscuit Wi-Fi scanning](https://codehedge.github.io/Biscuit-Wiki/features/wifi-scanning.html)) ([Biscuit capture and analysis](https://codehedge.github.io/Biscuit-Wiki/features/wifi-capture.html)) ([Biscuit Node documentation](https://codehedge.github.io/Biscuit-Wiki/devices/node.html)) ([Biscuit flasher repository](https://github.com/CodeHedge/biscuit_flasher))

Hak5's public repositories show a payload and customization ecosystem, rather than a reusable public device firmware base. Its Pager payload conventions are more relevant to Sightline than adopting a payload language: a task recipe declares purpose, targets, prerequisites, configurable values, visible status, and outputs. Its Pineapple documentation shows directed channel capture, while its update guide calls for firmware-image hash verification. Sightline can apply those principles to **named, reviewable recipes** that preview the exact target set, interface, limits, files, and expected network effect before launch, then save the recipe version and resulting artifacts together. Individual Hak5 payloads have their own provenance and terms; a clean Sightline recipe format is the sounder implementation. ([Hak5 repositories](https://github.com/hak5)) ([Pager payload repository](https://github.com/hak5/wifipineapplepager-payloads)) ([Pineapple recon documentation](https://docs.hak5.org/wifi-pineapple/ui-overview/recon-1)) ([Hak5 firmware setup](https://github.com/hak5/hak5-docs/blob/master/setup/setting-up-your-wifi-pineapple.md))

## Put bounded network tools on device and heavier suites beside it

Sightline already has local Nmap XML ingestion and a `tcpdump` capture wrapper. That is a strong product distinction: Nmap recommends XML for programmatic consumers, and a captured packet file can be independently inspected after the field session. The first native package set should add bounded DNS queries, HTTP header and TLS certificate checks with `curl` and OpenSSL, and targeted socket/banner checks alongside Nmap and `tcpdump`. Every run needs a named scope, selected interface/source address, host and port limits, time and output caps, cancellation, exit status, start/end time, tool version, exact arguments, and raw-output receipt. The UI should distinguish an observed open port or presented certificate from a confirmed vulnerability. NSE scripts need a reviewed allowlist: Nmap warns that its scripts are not sandboxed and categorizes intrusive, brute-force, denial-of-service, and exploit scripts separately from safe scripts. ([Sightline README](https://github.com/Zetascrub/Sightline/blob/main/README.md)) ([Sightline capture wrapper](https://github.com/Zetascrub/Sightline/blob/main/firmware/rootfs-overlay/usr/sbin/reconclave-capture)) ([Nmap XML guidance](https://nmap.org/book/output-formats-xml-output.html)) ([Nmap NSE guide](https://nmap.org/book/nse-usage.html)) ([curl manual](https://curl.se/docs/manpage.html)) ([OpenSSL `s_client` manual](https://docs.openssl.org/4.0/man1/openssl-s_client/))

**Wireless suites are conditional additions, not checked boxes.** Kismet needs a Linux driver with standard monitor-mode support; Aircrack-ng's capture and injection tools need suitable adapters and supporting libraries; hcxdumptool calls for monitor mode and full-frame injection and warns that even apparently suitable drivers can fail. Internal associated Wi-Fi operation does not establish any of these properties. The first wireless trial should use a specifically identified USB adapter, prove passive monitor capture with `iw phy` and packet inspection, verify power and connection behavior, and only then evaluate Kismet or `airodump-ng` with storage and performance measurements. Kismet's rich `kismetdb` and PCAPNG export can run on a workstation with the handheld as a remote capture source if local server overhead is too high. Transmitting radio functions need separate hardware and scope validation before inclusion. A `tcpdump` plus desktop Wireshark workflow is the initial packet-analysis path; TShark on device is an optimization to measure, since live capture depends on libpcap and privileges and its dissectors consume space. ([Kismet Linux Wi-Fi source](https://kismetwireless.net/docs/readme/datasources/wifi-linux/)) ([Kismet database logging](https://www.kismetwireless.net/docs/readme/logging/kismetdb/)) ([Aircrack-ng documentation](https://aircrack-ng.org/documentation.html)) ([hcxdumptool README](https://github.com/zerbea/hcxdumptool)) ([TShark manual](https://www.wireshark.org/docs/man-pages/tshark.html))

The workstation or Reconclave coordinator should handle **Metasploit, broad Nuclei template runs, high-rate Masscan, and offline password auditing**. Metasploit brings a Ruby/PostgreSQL-backed service and a web API; Nuclei's template corpus is broad and already excludes some disruptive tags by default; Masscan is explicitly built for high-speed asynchronous probes that can overload networks; and Hashcat requires a usable compute backend that has not been demonstrated on K230. Those are architectural placement choices, not claims that each program is impossible to cross-compile. Sightline should exchange Nmap XML, raw PCAP, DNS/HTTP/TLS observations, target coverage, and artifact hashes with the companion, then import reviewed results with tool version, scope, timestamp, and evidence links. ([Metasploit development setup](https://docs.metasploit.com/docs/development/get-started/setting-up-a-metasploit-development-environment.html)) ([Metasploit web service](https://docs.metasploit.com/docs/using-metasploit/advanced/metasploit-web-service.html)) ([Nuclei templates](https://github.com/projectdiscovery/nuclei-templates/blob/main/README.md)) ([Nuclei template exclusions](https://github.com/projectdiscovery/nuclei-templates/blob/main/.nuclei-ignore)) ([Masscan README](https://github.com/robertdavidgraham/masscan)) ([Hashcat FAQ](https://hashcat.net/wiki/doku.php?id=frequently_asked_questions))

## Deliver a credible first final release in four passes

The **first pass** is a measured hardware and software acceptance run on the exact unit: identify board and expansion revisions, radio chipsets and drivers, mounted storage, free RAM, USB port roles, kernel gadget options, and available tool versions; repeat the physical keyboard edit, touch typing, GPS, BLE, Wi-Fi, and USB Ethernet paths under the latest UI. The **second pass** is the core assessment release: scope-aware Nmap, DNS, HTTP/TLS, banner checks, and bounded `tcpdump`, all using one job lifecycle and one evidence schema, with Assets/Findings/History showing what was observed and what remains untested. The **third pass** adds reviewed recipes, operator-visible progress and cancellation, a keyboard command palette, export/import receipts, and a companion handoff that keeps raw artifacts intact. The **fourth pass** is an accessory track: validate one USB Wi-Fi adapter for passive capture, then profile Kismet/TShark and optional BLE HCI, USB gadget, LoRa, camera, and cellular paths individually. No feature should move from “available in a vendor SDK” or “built successfully” to “supported on Sightline” until its full capture or interaction path works on physical hardware. ([Sightline validation report](https://github.com/Zetascrub/Sightline/blob/main/docs/VALIDATION.md)) ([Vendor pin map](https://github.com/Xinyuan-LilyGO/T-Display-K230/blob/main/k230_bsp/docs/HARDWARE_PINMAP.md)) ([Kismet data sources](https://www.kismetwireless.net/docs/readme/datasources/datasources/))

## Conclusion

The strongest “packed” K230 is a **field instrument that produces trustworthy, portable evidence**, with enough native tools to answer immediate network and protocol questions and a companion path for deeper analysis. Breadth should come from a capability registry and recipe system that can grow as each radio, port, and accessory is validated. That design preserves the appealing immediacy of portable security firmware while using the K230 display, keyboard, Linux environment, and Sightline's existing asset history for work the smaller devices cannot present as clearly.

## Live device follow-up, 8 October 2026

After this survey, the connected Sightline unit reported Buildroot 2025.02.1,
Linux 6.6.36, roughly 900 MiB available RAM, and 181 MiB free rootfs space
before deployment. Its active `wlan0` was bound to the `rtl8189fs` SDIO driver;
the wired `eth0` was a USB `r8152` adapter. This resolves the chipset question
for **this unit and image**, without establishing monitor mode or injection.
The rebuilt image contains `dig`, `host`, `jq` and the runtime libraries they
need. Those tools were also installed and exercised on the running device:
`dig` returned an A record through the local router and `jq` parsed the
capability inventory. The UI rendered the new status panel in a DRM screenshot.
The device later became unreachable on both interfaces during a second
screenshot transfer, so sustained stability and physical keyboard interaction
remain open. The exact commands and validation limits are recorded in
[the on-board validation log](../docs/VALIDATION.md).
